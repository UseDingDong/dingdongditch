# Public machine contract

## Purpose

DingDongDitch is a deterministic execution runtime, not a model provider or
planner. Its public machine contract lets any host that can emit JSON propose a
bounded browser plan, parse it fail-closed, execute it through the ordinary
runtime, and consume typed receipts.

```text
planner -> PlanDocument JSON Schema -> parse_plan_document
        -> proposal -> GovernedAgentSession -> receipt -> host
```

No part of this contract invokes a model, stores API keys, retries a model, or
chooses browser actions. A host retains all reasoning, consent, and recovery
ownership.

For a new agent integration, `PlanDocument` is a proposal grammar, not an
execution capability. The host installs policy with `TrustedHostRuntime` and
exposes only `GovernedAgentSession` (or authenticated
`GovernedAgentService`) to the planner. Historic `execute_plan` and
`execute_operation` exports remain trusted-host/compatibility calls; do not
place them in an LLM tool set.

## Canonical input

The normative root for new integrations is `PlanDocument` version `1.0.0`:

```json
{
  "schema_version": "1.0.0",
  "browser": {"engine": "chromium", "channel": "bundled", "headless": true},
  "plan": {
    "plan_id": "example",
    "operations": [{
      "operation_id": "navigate",
      "url": "https://example.com",
      "action": {"type": "navigate"},
      "expectations": []
    }]
  }
}
```

`browser` is deliberately outside `plan`. A canonical document must include
`schema_version` and rejects unknown fields. `plan.browser_config`, bare plans,
and the older wrapper without `schema_version` remain accepted only through
`parse_execution_plan()` and the existing CLI as legacy compatibility input.
They are not the normative agent-integration format.

## Schemas and APIs

Schemas use JSON Schema Draft 2020-12. They are generated by
`dingdongditch.contract_schema` and committed under `dingdongditch/schemas/`.
The following public Python APIs return detached `dict` values:

The canonical input schemas additionally include optional `plan.authority_envelope`,
bounded `plan.speculative_plans`, operation `provenance`, and operation
`verification_quorum`. An envelope in a document is transportable review data,
not a self-authorizing grant: hosts install the envelope at a stateful session
boundary. Signed plans bind the complete canonical document, including its exact
speculative topology; planner-supplied signing, identity, attester, policy, and
handoff trust configuration is never accepted through this contract. Additive
receipt fields expose compact authority, transaction, quorum, receipt-chain,
identity, mutation, and speculation summaries. `prepared-operation`,
`agent-handoff-checkpoint`, `agent-handoff`, `signed-plan-authority`,
`agent-identity`, `identity-assertion`, `mutation-evidence`,
`execution-attestation`, and `speculative-plan` are separate canonical schemas
available from the same CLI schema command; none is vendor-specific.

| API | Schema |
| --- | --- |
| `plan_document_schema()` / `execution_schema()` | canonical PlanDocument |
| `execution_plan_schema()` | legacy-capable ExecutionPlan object |
| `operation_schema()` | one Operation |
| `observation_schema()` | PageObservation |
| `execution_receipt_schema()` | ExecutionReceipt 1.8.0 |
| `plan_receipt_schema()` | PlanReceipt 2.2.0 |

`published_schema_resource(name)` reads the exact JSON file installed with the
package. `dingdongditch schema list` lists resource names; `dingdongditch
schema <name>` writes valid JSON to stdout and supports `--output`.

Parsing and serialization are public too:

```python
document = dingdong.parse_plan_document(payload)
plan = dingdong.parse_execution_plan(payload)  # canonical or legacy input
wire = dingdong.serialize_plan_document(document)
receipt = dingdong.parse_plan_receipt(receipt_json)
```

`parse_receipt()` selects a receipt decoder by public shape. The decoder avoids
requiring a consumer to hand-inspect `plan_verdict` versus `verdict`.

## Validation boundary

The published input schema constrains known fields, enums, action variants,
frame paths, upload declarations, guard branches, and static numeric bounds.
The public parser always runs afterwards and remains authoritative.

JSON Schema cannot establish filesystem existence or authorization resolution,
browser/channel availability, profile locks, unique live-DOM target matches,
live frame existence, current page freshness, timing relationships that require
runtime state, or whether a browser expectation is true. Those are explicit
runtime validation boundaries and produce normal execution receipts or typed
runtime errors; schema validity never authorizes execution by itself.

`ContractValidationError.to_dict()` is the integration-facing static validation
format. It contains a contract version and bounded `ValidationIssue` objects
with a code, JSON Pointer, human message, expected constraint when known, and
safe observed type. It never includes secret values, upload paths, or whole
input payloads. Canonical-root errors are accumulated where independent;
deeper parser validation remains fail-closed.

## Receipts and observations

Execution receipts retain the Core Receipt / Bounded Evidence / Artifact
architecture. `ExecutionReceipt.to_layered_dict()` remains the recommended
new-consumer representation; the complete `to_dict()` payload validates
against `execution-receipt.schema.json`. CLI plan output is a `PlanReceipt` and
validates against `plan-receipt.schema.json`.

The public observation schema names the stable bounded structures that a
planner needs: element, region, visible text, overlay, geometry, locator
candidate, focus/document metadata, freshness, scroll context, and diagnostics.
Only genuinely variable evidence payloads retain bounded object escape hatches.

## Tool definitions and vendor projections

`execution_plan_tool()` returns the canonical model-neutral data shape:

```python
{
  "name": "execute_browser_plan",
  "description": "...",
  "input_schema": dingdong.execution_schema(),
}
```

Thin optional modules reshape only that data:

- `dingdongditch.adapters.openai.execution_plan_tool()` returns an OpenAI-style
  function envelope. `strict=False` is the lossless default; requesting
  `strict=True` fails explicitly because strict vendor modes may implement
  only a schema subset.
- `dingdongditch.adapters.anthropic.execution_plan_tool()` returns the
  Anthropic `input_schema` form.
- `dingdongditch.adapters.gemini.execution_plan_tool()` returns a Gemini
  declaration with `parametersJsonSchema` (or snake_case on request).

No adapter imports a vendor SDK, calls a model, owns a browser session, or
changes plan/runtime semantics. If a vendor accepts only a schema subset, use
the generic schema as the source of truth and still call
`parse_plan_document()` before execution.

## Compatibility policy

`MACHINE_CONTRACT_VERSION` versions PlanDocument independently of package and
receipt versions. A major contract version changes the canonical JSON grammar;
minor-compatible expansion keeps the major grammar valid and publishes a new
versioned schema resource. During the pre-1.0 package period, DingDongDitch
will document any breaking canonical-contract change in the changelog and keep
the prior schema resource for its supported compatibility window.

Missing `schema_version` is legacy-only. A canonical parse rejects it, and an
unknown version produces `unsupported_contract_version` at `/schema_version`.
Receipt versions are independently exact: ExecutionReceipt `1.8.0` and
PlanReceipt `2.2.0` for this release.

## Drift workflow

`contract_schema.py` is the one source for Python exports, CLI output, generic
tools, adapters, and generated schema resources. Tests assert that every
committed JSON resource equals the generator, public fixtures validate and
parse, runtime receipt/observation serialization validates, and adapters carry
the canonical schema without mutation. Run
`python scripts/refresh_machine_schemas.py` after changing that module; never
edit generated resources or vendor schemas independently.
